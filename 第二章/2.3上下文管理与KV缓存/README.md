# 实验2-3：上下文管理与KV缓存

参考[官方实验README](https://github.com/bojieli/ai-agent-book/blob/main/chapter2/kv-cache/README.md)的六种模式，制作本机Ollama学习对照。官方使用Kimi及真实文件工具ReAct任务；这里固定预设历史，真实请求qwen3:0.6b，工具仅以定义形式传入，不执行工具，不测厂商价格。本地API使用[Ollama兼容接口](https://docs.ollama.com/api/openai-compatibility)的流式正文及usage字段。

## 运行方式

在PyCharm用根目录共用解释器，运行[01_六种上下文方式对照.py](我的代码/01_六种上下文方式对照.py)。无需新依赖或模型下载；需要本机Ollama服务可用。

共37次请求：1次预热；六种模式各3对，每对先基础请求一次，再追加追问并修改一个条件。只汇总追问轮，原始输入、工具顺序、输出、用量和指标逐对保存。

| 模式 | 基础请求与追问之间的差异 |
| --- | --- |
| correct | 保留历史，只追加助手回答及新问题 |
| dynamic_system | 系统消息开头的时间改变 |
| dynamic_profile | 系统中的用户剩余额度改变 |
| shuffled_tools | 三个工具定义循环移位，确保顺序改变 |
| sliding_window | 保留系统消息，历史只留最后5条 |
| text_format | 把结构化历史转换为一条USER/ASSISTANT纯文本消息 |

各对有唯一实验编号，减轻跨对前缀复用；不同模式配对顺序固定随机打乱。服务仍可能复用公共工具前缀。没有主动清空服务缓存，基于各对基础请求建立缓存后观察追问。

## 同时看缓存和回答

最早历史记录项目归档编号，最后追问它。保存两个独立判断：能否找回原编号、回答是否符合当前实际输入。滑动窗口删除编号后，UNKNOWN符合输入证据，但原始信息已丢失；缓存高不表示信息保留完整。

首段正文延迟近似TTFT；缓存比例按服务报告的cached_tokens/prompt_tokens计算，字段缺失记未知。每组3次只做本机观察。动态内容所在位置、工具序列化和稳定系统长度都会影响结果，不预设所有改动都降低缓存。

纯文本的首次转换会改变序列，长期固定的纯文本仍可以命中缓存；本实验不将“结构化”与“必然命中”画等号。模型格式适配与缓存复用需要分别判断。

成功标志KV_OBSERVATION_COMPLETE，只说明配对测量完成，不表示回答全部正确或原书预期现象全部出现。遇到截断、工具请求或连接失败保存部分结果并退出；助手未执行实验。
