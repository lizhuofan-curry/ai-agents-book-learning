# 本地通知与定时器

当前为第一步本地实现，代码由助手准备，用户已实际运行并完成结果核对，见[20结果小结](20_本地通知与定时器结果小结.md)。下文为复现说明，不需重跑成功案例。使用[18_本地通知与定时器.py](我的代码/18_本地通知与定时器.py)，不需要Ollama或新依赖。

## 先区分三件事

1. **计时器**保存何时到期、是否循环及是否取消。
2. **调度循环**不断查看哪些计时器到期；本例是同一个Python进程每约20毫秒检查一次。
3. **通知回调**在到期时执行，本例只把消息写进当前运行目录的notifications.jsonl和终端。

“设置成功”只表示任务已登记；“回调触发”与“输出成功”分别记录。终端写成功不证明人已读到。这里的通知是本地应用输出，不是macOS系统横幅，也不是邮件、微信或Slack送达。

## 现在怎么做

在项目根目录运行，或VS Code打开18脚本使用项目`.venv`解释器直接运行：

```bash
.venv/bin/python '第四章/4.5协作工具/我的代码/18_本地通知与定时器.py'
```

本次0次模型、MCP或网络请求，只创建新的本地运行目录。脚本自动观察约4.5秒，不需要你在终端回复。

| 计时器 | 预设行为 | 最终应有的通知数 |
| --- | --- | ---: |
| once_demo | 2秒后触发一次 | 1 |
| cancelled_demo | 原定4秒后触发，进入等待前已由程序取消 | 0 |
| recurring_demo | 间隔1秒，观察到第3次后由程序取消 | 3 |

取消是本次教学代码固定执行，不冒称你亲自点击了取消。先观察状态流转，之后再练习修改参数。可能先看到循环提醒，再看到一次提醒；临近同一时刻的输出先后顺序不作为验收条件。

脚本会观察到被取消计时器原定期限之后，再核对它未触发。正常总共4条本地通知，最后打印通知数、检查项及record.json路径。把终端输出和路径发回核对。

`--preview`只说明入口，不计时、不创建目录。

## 看哪几处代码

- `set_timer`：登记截止时间，状态为pending。
- `tick`：到期后进入firing，调用本地通知；一次任务成功后为fired，循环任务回到pending等待下一次。
- `cancel`：pending变成cancelled，之后的tick跳过它。已完成、已取消或未知编号的再次取消不会触发动作。
- `notification_sink`：分别记录日志写入和终端写入；输出失败时计时器标记failed，不自动重试。

先想清楚：取消后为什么不会再调用通知？如果计时器到期了但程序没运行tick，会立即出现通知吗？这些问题可直接从条件判断中找到依据。

## 记录和限制

每次新建`运行结果/local_timers_时间/record.json`及`notifications.jsonl`。记录含脚本与官方参考README哈希、设置/到期/取消事件、各计时器状态、实际通知内容及通道写入标记、最后检查。已取消项保留状态，不靠删除记录表现取消。

用time.monotonic计算等待时间，墙上日期只用于记录。操作系统调度、进程忙碌或休眠可能导致延迟，不能把本例当成硬实时定时器。循环采用固定延迟：一次通知结束后再等待一个间隔，不补发休眠时错过的次数。若机器卡顿导致4.5秒内不足3次，会如实显示检查未通过，不补造事件或自动延长至成功。

JSON是本次状态快照，不是持久调度服务。关掉进程就没有后续回调，重新运行只开始新批次，不恢复旧任务。当前不覆盖跨进程并发、重启恢复、长期无人值守、外部消息渠道、系统通知或真实MCP工具调用，也不算官方全部范围完成。

本机正常运行后，可用虚拟时钟观察到期前/到期时的边界，或亲手改一个本地延迟；修改实验规则前先明确新的预期，不编辑已经保存的记录。
