# 第三步：本地模型选择并调用MCP工具

打开`我的代码/04_本机模型选择并调用MCP工具.py`点击运行。它会切换到已安装的第四章SDK环境，无需手动切换解释器，不自动安装或下载。

```bash
.venv/bin/python "第四章/4.2感知工具/我的代码/04_本机模型选择并调用MCP工具.py"
```

Ollama需正在运行且本地已有qwen3.5:9b。固定问题为“请读取‘工具说明.txt’，告诉我这个实验要做什么。”最多两次本机模型请求、一次MCP工具调用，温度0、种子42、输出上限1024、上下文16384；不预热、不重试、不调用云端或下载模型。

## 一次完整流程

1. 客户端连接SDK文件服务，获得实际工具目录。
2. 客户端把MCP工具的名称、说明、inputSchema转换为Ollama的tools声明，与问题一起发送；不预先发送文件正文。
3. 模型返回原生tool_calls，选择名称及参数。客户端检查它确实选择一次file_reader，且路径为用户指定文件；不代写调用或纠正路径后偷偷执行。
4. 客户端使用SDK call_tool，服务端实际读文件。记录完整工具结果，并检查是否等于原文件。
5. 按Ollama格式保留assistant的工具调用消息，再追加role=tool、tool_name及实际返回内容，发起第二次请求。
6. 模型给出最终回答。第二次不再提供工具声明；若仍请求工具、无回答、被截断或异常，保留未完成记录并停止。

MCP SDK负责客户端到工具服务端的协议；Ollama tools字段负责向模型介绍工具，两者由我们编写的客户端衔接。模型不直接连接文件系统或MCP服务。当前只有一个工具且用户明确要求读文件，所以这只是自主发起调用的入门例子，不能证明模型能在复杂目录中选对工具。

## 看输出时分清三层

- 模型选择：它是否真的返回工具调用，参数是否正确。
- 工具事实：是否成功读到完整正文，原文件检查是否一致。
- 模型回答：是否忠于返回内容，有没有补造或混淆文件描述与本轮实际过程。

测试文件沿用前两步，正文里“不调用大模型”是旧文件的内容；本轮流程实际会请求模型。解释文件内容不等于证明本轮没有模型请求，后续审阅要区分两者。

结束标记MODEL_MCP_RUN_SAVED只表示轨迹保存。应同时查看状态：model_mcp_answer_saved_review_pending表示完整读取及回答已保存、语义待核对；tool_result_incomplete_answer_review_pending表示读取失败或不完整但有回答；incomplete表示流程未完成。格式和原文匹配不自动证明回答正确。

完整模型请求、原始HTTP响应、模型原消息、工具目录、SDK解码结果、环境版本及源码哈希写入新运行目录，不覆盖前两步。SDK保存的是解码结果，不是底层stdio逐字记录。
