# 第二步：把执行函数注册为MCP工具

打开`我的代码/03_通过MCP写入运行与核对.py`点击运行。它会切换已有SDK环境，不需要手动换解释器，不自动安装或下载；不用启动Ollama。

```bash
.venv/bin/python "第四章/4.4执行工具/我的代码/03_通过MCP写入运行与核对.py"
```

任务与01保持一致，仍是正确词频、语法错误和故意算错三种情况。区别在调用途径：01在一个进程里直接调用函数；03连接独立SDK服务端，列出三个工具，再将名称和参数通过真实stdio送给服务端，由服务端调用原来的函数执行并返回结果。

| 工具 | 实际工作 | 结果表示什么 |
| --- | --- | --- |
| file_write | 在本轮工作区写文件，Python先检查语法 | success表示写入是否完成 |
| run_python | 子进程运行已知固定脚本 | success和returncode只说明执行状态 |
| verify_counts | 读取实际counts.json并按输入独立计数 | goal_correct表示产物是否满足词频任务 |

工具由我们本地注册，不是SDK自带。SDK负责目录生成、调用分发及协议通信，内部功能仍复用执行工具教学实现.py。客户端只固定调用，不让模型规划。本步骤不把固定代码当作模型编写，也不测试自动修复。

客户端共9次工具调用：准备输入、写入正确代码、尝试语法错误、运行/验证正确版、准备错误版输入、写入逻辑错误、运行/验证错误版。所有调用前后的参数和SDK解码结果写入记录；不声称记录了原始stdio逐字消息。模型和网络请求均0。客户端额外打开两个结果文件检查实际内容，记录全部产物哈希。

重点观察：语法错误的写入返回isError=true；逻辑错误的运行返回success=true、returncode=0；验证工具正常完成时isError=false，却返回goal_correct=false。后一种表示“验证正常执行并发现错误”，不等于协议失败。

每次新建两个独立版本工作区，不覆盖旧运行；只执行与已知两段源码完全一致的脚本，不执行任意代码。不提供Shell或外部账号工具，独立工作目录也不等于OS安全沙盒。本练习不是官方4-4全套验收。

--preview仅检查环境及文件；--check在临时目录执行真实MCP流程但不生成正式结果。预览、真实stdio检查和3项离线测试通过，覆盖进程到真实文件的执行链、目标错误检测、工作区缺失/链接拒绝及缺失脚本错误。正式运行待用户完成。

看到MCP_EXECUTION_RUN_SAVED后发回输出，先理解各层成功含义，再考虑是否引入本地模型。所有受控错误被按预期发现，才表示这次教学检查通过。
